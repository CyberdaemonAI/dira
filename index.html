Dual-Intent Runtime Authorization

DIRA is a framework for authorizing AI agent actions at runtime, verified against declared intent, not just assigned role.

The gap: static access control cannot distinguish a read-access agent summarizing a document from one exfiltrating it. The action is the same. The intent is not. No current framework makes enforcement decisions at that boundary.

200-Level

Why Existing Authorization Fails for AI Agents

Role-based access control (RBAC) and attribute-based access control (ABAC) were designed for human principals making deliberate, bounded requests. A user logs in, presents credentials, and requests a specific resource. The authorization model evaluates that request against a policy: does this principal, with these attributes, have permission for this action on this resource? The model assumes the principal is a human whose intent is implicit in the request itself. Requesting a file read means you want to read the file. Period.

Autonomous agents break that assumption completely. An agent with read access to a document corpus can perform fundamentally different operations under the same permission grant: summarizing content for a user query, building an index for a legitimate pipeline, or systematically staging data for exfiltration. The permission is identical. The authorization check passes in all three cases. The difference between a compliant agent and a compromised one is not visible at the policy evaluation layer, because the policy layer was never designed to see it.

The audit trap: "We log everything" is not authorization. Audit logging records what happened after the fact. The value of a control is its ability to prevent unauthorized action, not to document it. An authorization system that detects a data exfiltration event in the audit log has failed at the one thing authorization exists to do. The control point is before the action executes, not after it completes.

The problem compounds in multi-agent systems. Modern agentic architectures involve orchestrators delegating tasks to subagents, tool-calling chains where a single user request fans out into dozens of downstream actions, and autonomous agents invoking other agents. At each delegation boundary, the original authorization context degrades. An orchestrator with user-delegated authority spawns a subagent that inherits that authority implicitly. That subagent may invoke a tool that was never contemplated in the original delegation. The permission chain grows. The intent verification chain does not exist. This is the principal confusion problem: the system cannot distinguish between an action the user authorized and an action that happened to fall within scope of what the user authorized, for reasons entirely unrelated to user intent.

The consequence is an authorization model that is technically functional and operationally blind. Agents pass every check because the checks were designed for actors who cannot disguise or misrepresent intent at the system level. Humans can, but they face monitoring, accountability structures, and legal liability. Agents face none of those. The behavioral control that compensates for absent legal and social accountability in human systems simply does not exist for autonomous agents in any current framework.

300-Level

The DIRA Framework

DIRA defines three core principles for behavioral authorization. Together they close the control gap that static permission models leave open. Each principle corresponds to a specific failure mode in existing systems.

Principle 01

Intent Declaration

Every agent action must carry a declared intent payload at invocation time. Before an agent calls a tool, accesses a resource, or invokes an API, it must declare what it is trying to accomplish, in a structured, machine-readable format. The declaration is not a comment or a log entry. It is a required input to the authorization decision.

The payload includes: the action type (read, write, transform, transmit), the target resource, the declared purpose (summarize, index, forward, archive), the originating task context, and the identity chain of any orchestrating agents above it in the call stack. This payload travels with the invocation, not separately, so it cannot be stripped or forged at the transport layer without detection.

Why it matters: Authorization systems that cannot observe intent cannot distinguish compliant from non-compliant behavior when the action type is identical. Requiring declaration creates an observable signal. It also creates accountability: a declared purpose that does not match observed reach is a specific, auditable anomaly, not an ambiguous behavioral pattern.

Principle 02

Dual Verification

Authorization checks declared intent against observed scope reach, in addition to checking role membership. The first check is traditional: does this principal have permission to perform this action type on this resource? The second check is new: does the observed resource access pattern match what the declared intent would predict?

An agent declaring "summarize document for user query" should access a bounded set of resources consistent with that task. If the observed scope reach extends significantly beyond that set, accessing unrelated documents, external endpoints, or high-volume sequential reads inconsistent with a summarization task, the second check fails. The authorization engine does not need to classify the intent as malicious. It only needs to detect divergence between what was declared and what was observed.

Why it matters: Single-dimension authorization (role membership only) cannot detect behavioral deviation within a permitted scope. Dual verification creates a second enforcement axis. An agent can pass the role check and fail the behavioral check. Both checks must pass. Neither alone is sufficient.

Principle 03

Invocation-Time Enforcement

The enforcement point is at invocation, not in the audit log. When an agent calls a tool or API, the DIRA authorization engine evaluates the intent declaration and the predicted scope profile before the call executes. A deny decision blocks the action. An anomaly signal routes to a monitoring or escalation path. The action does not proceed while authorization is unresolved.

This requires the enforcement point to sit between the agent and the tool or API, not downstream of it. In practice this means the DIRA engine is a sidecar, a gateway, or an SDK-level intercept, depending on the deployment model. The architectural requirement is that no tool call reaches its target without passing through the enforcement layer.

Why it matters: Enforcement after the fact is not enforcement. A system that detects unauthorized behavior in a post-hoc audit has failed the agent it was supposed to constrain. Invocation-time enforcement is the only model where authorization actually functions as a control, not as a record of failures.

The Gap in Current Frameworks

Several active frameworks address adjacent problems in agentic AI security. None of them define runtime intent verification as an enforceable control category. The table below maps what each framework addresses and where the gap remains.

SPIFFE/SPIRE provides the identity plane that a DIRA implementation would build on top of. Identity verification is a prerequisite, not a substitute. The frameworks listed above solve real problems. The point is not that they are wrong but that the gap they collectively leave is not incidental. It corresponds precisely to the authorization problem that is most acute in agentic AI systems.

Component Descriptions

Intent Declaration Layer. Sits at the agent SDK or tool-call boundary. Accepts the agent's outbound action and requires attachment of the intent payload before forwarding. Stateless. Can be implemented as an SDK wrapper, a sidecar proxy, or an API gateway plugin. Blocks any invocation that does not carry a valid intent declaration.

DIRA Authorization Engine. The core decision service. Receives the declared intent payload alongside the action request. Runs two checks in parallel: scope verification against the configured resource policy, and behavioral verification against the predicted scope profile for the declared purpose. Returns a grant, a deny, or an anomaly signal with context.

Scope Check. Evaluates the action request against standard access control policy: role membership, attribute predicates, resource permissions. This is the existing authorization check that most systems already perform. DIRA does not replace it. It adds a second axis.

Behavior Check. Evaluates the predicted resource reach for the declared intent against the observed or requested scope. A summarization task has a predictable reach profile. A data export task has a different one. Divergence between declared purpose and actual scope reach triggers the anomaly signal path. The check does not need to classify intent as malicious to be useful. Detecting divergence is sufficient.

Anomaly Signal. Not a deny decision. Routes the invocation to a monitoring, escalation, or rate-limiting path while the scope check result is still evaluated. An anomaly on the behavior check does not automatically block the action, but it flags the session for elevated scrutiny and can feed session-level drift tracking. In high-trust environments, anomaly signals may trigger human-in-the-loop review.

Action Executes. The action reaches its target only when both checks pass. If the scope check denies, the action is blocked. If the behavior check signals an anomaly and policy dictates block-on-anomaly, the action is blocked. The target system sees no indication of a blocked request unless explicitly surfaced through an error response.

400-Level

Implementation Considerations

For practitioners building a DIRA-style system, the following sections address the key design decisions: what to put in the intent payload, where the enforcement point lives, what anomaly detection actually means in practice, and how to wire it into existing infrastructure.

The Intent Declaration Payload Schema

The payload must be machine-readable, signed by the agent identity, and immutable once declared. A minimal schema includes:

action_type: "read" | "write" | "transform" | "transmit" target: "resource identifier or URI pattern" declared_purpose: "summarize" | "index" | "forward" | "archive" | ... task_id: "originating task or session identifier" principal_chain: ["orchestrator-svid", "subagent-svid"] # SPIFFE SVIDs scope_assertion: "predicted resource reach as set or pattern" timestamp: "ISO-8601 with millisecond precision" signature: "agent SVID signature over payload hash"

The principal_chain field is critical for multi-agent systems. It carries the full delegation stack, not just the immediate caller. Each entry is a SPIFFE Verifiable Identity Document (SVID), making the chain cryptographically verifiable. The scope_assertion field is the agent's self-declared prediction of what resources it expects to touch. This is what the behavior check evaluates against observed reach.

Enforcement Point Placement Architecture

The enforcement point must sit between the agent and the tool or API call. Three deployment patterns are viable:

SDK intercept. A wrapper around the agent's tool-calling library that attaches intent declarations and routes through the DIRA engine before dispatching. Works in environments where you control the agent code. Lowest latency, highest coverage.

Sidecar proxy. A lightweight sidecar container (or process) that intercepts all outbound calls from the agent process. Works for containerized agents without code modification. Requires network-level interception, similar to service mesh patterns. SPIFFE workload attestation integrates naturally here.

API gateway plugin. A plugin or policy layer at the API gateway that enforces intent declaration as a precondition for routing. Works well when agents access a bounded set of internal APIs. Less effective for arbitrary HTTP calls.

Regardless of deployment model, the enforcement point must be the only path to the target. Bypass routes defeat the control. This is the same architectural requirement as Zero Trust microsegmentation: if there is an uncontrolled path, the control does not exist.

What "Anomaly Signal" Means in Practice Detection

The behavior check generates an anomaly signal when the observed or requested scope reach diverges from what the declared purpose predicts. This is not a classification problem and does not require a trained model to get started. A rule-based implementation is sufficient as a baseline:

A summarize action targeting three documents should not request read access to 300. A forward action with a declared target of an internal endpoint should not resolve an external domain. A transform action should not generate write traffic to a storage endpoint not listed in its scope assertion. These rules are deterministic and auditable.

At higher maturity, the behavior check can incorporate statistical baselines: the typical scope profile for a given agent identity and declared purpose type, derived from historical sessions. Deviation from the statistical baseline, rather than from a fixed rule, gives more sensitivity in complex environments where permitted scope is inherently variable.

Session-Level Drift Tracking Detection

A single anomaly signal may be a false positive: an agent legitimately needing to access more resources than its initial scope assertion predicted. But a pattern of anomalies across a session, or a progressive drift in declared purpose versus observed reach over time, is a stronger signal than any individual check.

Session-level drift tracking maintains a per-session behavioral profile that accumulates the declared intent and observed scope for every action in the session. A session where declared purpose shifts from summarize to index to transmit in a short window, each check passing individually, may trigger a session-level alert even though no single check failed. The session context is what makes the pattern visible.

This is also the mechanism for detecting multi-step attacks: where a compromised agent proceeds through a sequence of legitimate-looking individual actions whose aggregate effect is unauthorized. No single invocation fails the DIRA check. The session drift check catches the pattern.

Integration with SPIFFE / SPIRE Identity Plane

SPIFFE/SPIRE is the identity foundation that DIRA builds on top of, not a substitute for it. SPIFFE provides the cryptographic workload identity (SVID) that makes the principal_chain field in the intent payload verifiable. Without a reliable, attestation-backed identity for each agent in the delegation chain, the intent declaration cannot be trusted, because any agent could claim to be any other agent.

The integration pattern is: SPIRE attests the workload and issues an SVID. The agent holds its SVID in-memory via the Workload API. When constructing an intent declaration, the agent signs the payload with its SVID private key. The DIRA engine verifies the signature against the SPIFFE trust bundle before processing the authorization check. This ensures the declared intent comes from the claimed principal.

For multi-agent delegation chains, each agent in the chain signs and appends its SVID to the principal_chain array. The DIRA engine validates the entire chain, not just the immediate caller. This is the mechanism that closes the principal confusion problem: every delegation hop is cryptographically accounted for.

Research Status and Open Questions

This is active independent research. DIRA is not a ratified standard, a published specification, or a vendored product. It is a framework developed through analysis of existing authorization models and the specific failure modes they exhibit in agentic AI contexts. The following questions remain open and would benefit from empirical implementation work.

Open Research Questions

  • How should the scope assertion in the intent payload be structured for agents operating in open-ended task contexts where resource reach is genuinely unpredictable at declaration time?
  • What is the minimum viable behavioral baseline for a new agent identity with no historical session data? How should cold-start risk be managed?
  • How should the DIRA engine handle intent declaration for agent-to-agent calls where the downstream agent does not yet support the declaration protocol?
  • What is the appropriate escalation path when the behavior check signals an anomaly in a fully autonomous pipeline with no human in the loop?
  • Can session-level drift detection be implemented without creating new privacy risks through behavioral profiling of agent sessions that may carry user data?
  • How does DIRA interact with prompt injection attacks, where an adversary attempts to override a legitimate agent's declared intent through injected instructions in retrieved content?
  • What implementation evidence would validate or falsify the core dual-verification claim: that checking declared intent against observed scope catch meaningfully different threats than scope checking alone?

Implementations that test these questions, whether confirming or challenging the framework, are the most valuable contributions the research community can make to this problem space. The framework is not an answer. It is a structured way of asking the right questions.
